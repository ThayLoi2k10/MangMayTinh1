===== SLIDE 3 =====
Why this project exists
The assignment is intentionally closer to a real networked system than a toy chat app.
Commercial collaboration tools often depend on centralized third-party infrastructure.
This project asks you to build a lightweight, self-hosted alternative for LAN / VPN environments.
Latency and packet loss are real.
Connections fail unexpectedly.
Data should not rely on an external cloud.
Communicate on the local network.
Discover active users.
Transfer messages and files reliably.
The learning objective is not “build another Teams.” It is “understand the network mechanisms underneath.”

===== SLIDE 7 =====
First: read the transport requirements carefully
The brief mixes TCP, UDP streaming, and application-layer reliability. Do not hide this ambiguity.
WHAT THE BRIEF SAYS

Technique section: TCP for reliable file/message transfer; UDP for heartbeat/discovery.
Milestone 2: basic TCP handshake.
Milestone 6: reliable file transfer over UDP.
SAFE IMPLEMENTATION INTERPRETATION
Use TCP where the rubric explicitly asks for TCP handshake/control.
Use UDP for discovery/heartbeat.
Implement streaming/file reliability at the application layer over UDP where required.
Confirm the final transport split with the instructor before freezing the protocol.

===== SLIDE 28 =====
Common ways this project goes wrong
Most failures come from protocol design debt, not from the UI.
×
Start coding before packet/state design
Result: incompatible client/server assumptions
×
Treat UDP as “TCP but faster”
Result: loss, duplicates, and reordering break correctness
×
One thread handles everything
Result: one slow socket freezes all users
×
No explicit transfer/session ID
Result: fragments from different messages get mixed
×
Encryption added on the last day
Result: key handling and serialization break
×
README only works on author’s laptop
Result: project cannot be reproduced
Teaching guidance based on the brief requirements
