I. INTRODUCTION
1. CURRENT PRACTICES
With the rapid global shift toward remote work, distributed teams, and decentralized systems, reliance on
robust, real-time network applications has never been higher. Modern organizations require seamless
data exchange over local and wide-area networks, while navigating challenges like latency, packet loss,
and data security. Understanding how to build resilient network software from the ground up is a critical
skill for today’s software and network engineers.
2. THE NEED FOR THIS APPLICATION
While commercial solutions (like Slack, Microsoft Teams, or cloud storage) exist, they often route data
through centralized third-party servers, which can raise privacy, compliance, and bandwidth concerns for
closed-network environments. There is a distinct need for a lightweight, secure, and self-hosted network
application that allows users on the same network (or VPN) to communicate and share data directly
without relying on external corporate infrastructure.
3. GOAL OF THE APPLICATION
The goal of this project is to build aDistributedandStreaming-basedClient-ServerCollaboration
Application. Students will design and implement a custom application layer protocol over UDP
STREAMING that enables real-time messaging, active user discovery, and reliable file transfer between
multiple clients over a network. Due to the native requirement of messaging application,reliable
communication must be provided.
4.FeaturesoftheApplication
 UserAuthentication&Discovery: Users can log in, broadcast their presence, and see a live list
of other active peers on the network.

 Streaming-basedMessaging: Support for both broadcast (global chat) and unicast (private
direct messaging). ReferSteamGameNetworkingSocket andGoogleQUIC for message-
oriented transport layer.
 ReliableFileTransfer: The ability to send and receive files of various formats and sizes without
data corruption.
 ConnectionResilience: The app gracefully handles sudden client disconnects, timeouts, and
network interruptions.
 SecureDataTransmission: Basic encryption applied to the payloads to prevent packet-sniffing
vulnerabilities.
5.TargetUsers
 Internal corporate teams operating on secure, air-gapped, or isolated local area networks (LAN).
 Students or study groups needing a fast, peer-to-peer way to collaborate and share files without
internet access.
 Privacy-conscious individuals who prefer self-hosted communication tools.
6.TechniquesandTechnologiesIntegrated
 SocketProgramming: Implementation of TCP (for reliable file/message transfer) and UDP (for
heartbeat/discovery broadcasts).
 Concurrency: Multi-threading or Asynchronous I/O to handle multiple simultaneous client
connections without blocking the main thread.
 Application-LayerProtocolDesign: Designing custom packet structures (Headers, Payloads,
End-of-Message flags).
 Sequencingandordering : Maintaining monotonic sequence number with window-based sliding
window for flow control and in-order delivery.
 AcknowledgementandRetransmission: Efficient retransmitting of only missing segments.
 Congestioncontrol: Support streaming specific with BBR / CUBIC streaming support.
 Cryptography: Integration of TLS/SSL sockets or symmetric encryption (e.g., AES) for data
payloads.
 Serialization: Encoding and decoding structured data (JSON, XML, or custom binary packing)
over the wire.
7.DesignRequirements
 Architecture: Must clearly separate network logic, data processing, and the user interface.
 Time-sensitivestreaming : The system must provide an async mechanism to fetch data from a
stream without any. The streaming only handles chunk of bytes in UDP and leaves your protocol
logics in application layer in which you eliminate Head-of-line (HoL) blocking.
 UserInterface: Can be a clean Command Line Interface (CLI) or a Graphical User Interface
(GUI). It must be intuitive and display network status clearly.
 Scalability: The server/tracker must be capable of handling at least 10-20 concurrent clients
efficiently.

8.TechnicalRequirements
 ProgrammingLanguage: Python, Java, C++, or Go (Instructor to confirm restricted languages, if
any).
 NoHigh-LevelNetworkingLibraries: Students must use raw sockets (socket library in Python,
